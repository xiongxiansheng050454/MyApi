# 计费（预冻结 + 结算）· 限速限额 · 用量统计口径

本文件描述下游一次调用背后的**计费口径、限速限额语义、用量统计口径**。管理端查询入口见 [stats-billing.md](../02-管理端接口/stats-billing.md)。

---

## 1. 计费模型总览

### 1.1 涉及的数据

| 概念 | 来源 | 说明 |
| --- | --- | --- |
| 单价 | `model_pricing` | 渠道×模型，美元 / 1M tokens：输入价、输出价、可选 cached 输入价 |
| 费用计算 | 每请求实时 | `实际费用 = Σ(各类token数 × 单价)`，单位美元 |
| 费用快照 | `usage_logs` | 每请求落一行，存单价快照与总费用，防止后续改价影响历史 |
| 用户余额 | `user_balances` | `available_balance` 可用 / `frozen_balance` 冻结 |
| 资金流水 | `balance_transactions` | `freeze / consume / unfreeze / refund / recharge` 明细 |
| 日汇总 | `user_daily_stats` | 按 (user_id, date) 聚合费用 / token / 次数 |

### 1.2 费用公式

```
实际费用 = input_tokens × input_price
         + output_tokens × output_price
         + cached_input_tokens × cached_input_price   (若上游返回缓存用量且配置了缓存价)
         单价单位 = 美元 / 1M tokens
```

> 网关对**已发送到上游**的调用记账（成功按 usage；异常按 §2.3 的输入/输出分词估算）。网关侧被拒（鉴权/限流/余额不足/未发送上游）不产生费用。

---

## 2. 预扣（Redis） + 结算（DB）

采用**预扣 → 转发 → 实扣**：预扣在 Redis 中完成（Lua 原子、可过期、崩溃不影响数据库），结算时**先写数据库、再"多退少补"Redis**。

### 2.1 预扣（Redis，上游调用前）

1. 费用估算（选定渠道后按该渠道 `model_pricing`）：
   ```
   预估额 = 分词器输入token × input_price
          + 输出预算token × output_price
   ```
   - 输入 token：**专业分词器**（tiktoken，未知模型回退 `billing.default_encoding`，默认 `cl100k_base`）对 messages 计数。
   - 输出预算：`max_tokens`/`max_completion_tokens`，未传取 `billing.default_output_budget`（默认 1024）。
2. Redis 余额缓存 `bal:{uid}`（Hash：`v` 可用余额微单位、`gen` 重建代），TTL `billing.balance_ttl_seconds`：
   - 缓存缺失 → **双重检查锁**重建（`SET bal:lock:{uid} NX PX lock_ttl` → 二次检查 → 读 DB `available_balance` 写入）。
   - Lua 原子校验并扣减 `v`；不足 → `429 insufficient_quota`；成功返回 `gen`。
   - 无单价模型：仅校验 `v > 0`。
3. Redis 不可用 → 直接拒绝（`503`），`billing.enabled=true` 时强依赖 Redis。

### 2.2 结算（DB 权威，随后调整 Redis）

设预扣 `e`、实际 `a`（微单位）：

1. **先写数据库**：`usage_logs` 落库 → `user_balances.available_balance -= a`（行锁）→ `balance_transactions` 记 `consume -a`。
2. **再调整 Redis**：`bal.gen` 与预扣返回的 `gen` 一致 → `v += (e - a)`（多退少补）；不一致/缓存缺失 → `DEL bal`（下次以 DB 重建，避免重复扣）。

DB 侧不再产生 `freeze/unfreeze` 流水（`frozen_balance` 恒 0，字段保留兼容）。

### 2.3 上游异常计费

| 场景 | 处理 |
| --- | --- |
| 1. 只预扣、未发送上游（解密/构建请求失败等） | 仅释放 Redis 预扣，不写 `usage_logs` |
| 2. 已发送、上游未返回（网络错/超时/5xx） | 按**分词器输入 token** 计费：写 `usage_logs(status=error, input=分词器, output=0)` → DB 实扣输入费用 → Redis 退输出预算；**每个已发送的候选尝试各计一次** |
| 3. 中途崩溃/流式断开 | input=分词器输入，output=对**已收完整 SSE 块**的 delta 文本分词估算 → DB 实扣 → Redis 调整 |
| 正常返回 usage | 以 usage 为准（含 cached 折扣） |

- 4xx 业务错误透传不收费。
- 充值/管理端改余额后 `DEL bal:{uid}`（下次重建）。

## 3. 限速与限额（下游）

### 3.1 规则模型（`rate_limit_rules`）

| 属性 | 取值 | 说明 |
| --- | --- | --- |
| `target_type` | `global / user / api_key / model / channel` | 作用对象维度 |
| `target_value` | 具体 id 或 `*` 通配 | 如 `user=12`、`api_key=34`、`model=gpt-4`、`*` |
| `metric` | `rpm / tpm / rpd / tpd / concurrency` | 限流指标 |
| `limit_value` + `window_seconds` | 如 `60` 秒窗口 `600` 次 | 窗口内上限 |
| `action` | `reject / queue` | 超限时拒绝 或 排队（`extras` 配超时时间） |
| `priority` | 整数，越小越优先 | 多个规则命中时按优先级评估 |

语义：

| metric | 含义 | 计量 |
| --- | --- | --- |
| `rpm` / `rpd` | 每分钟 / 每天**请求次数** | 窗口计数 +1/请求 |
| `tpm` / `tpd` | 每分钟 / 每天 **token 量** | 累计请求估算或实际 token（按上游 usage，成功后记账） |
| `concurrency` | 并发在途请求数 | 当前处理中请求计数 |

- **全局令牌**按 (target_type, target_value, metric, window) 建立独立计数器，Redis 实现**自研滑动窗口**（时间按窗口拆桶，仅保留当前桶与前一个桶，`估算 = 当前桶 + 前一桶 × (窗口剩余比例)`），桶按 TTL 自动过期，内存有界。
- token 类指标（tpm/tpd）在请求前按**输入内容近似估算**（rune 数 ÷ `rate_limit.chars_per_token`）预估计入；`concurrency` 为 **Redis 全局在途计数**（INCR/DECR + TTL 兜底），随请求结束（含流式结束/客户端断开）释放。
- Key 级覆盖：`client_api_keys.rate_limit_overrides` 里的值**优先于**通用 user 规则（直接采用，窗口按默认 60s/86400s 归类，见 §3.2）。
- `queue` 动作：超限请求按 `extras.queue_timeout_seconds`（缺省 5s）轮询等待滑窗放行；等待超时返回 `429 engine_overloaded`。

### 3.2 生效顺序（同指标取"更严"）

1. 命中 Key 级 `rate_limit_overrides`（若配置，直接采用）。
2. 否则按优先级取命中的规则：`api_key` 特定规则 → `user` → `model` → `global` 通配；同优先级取数值更严者。

### 3.3 超限响应

超限返回下游 `429 rate_limit_exceeded`（OpenAI 风格），并携带 `Retry-After`（秒）。排队模式超限但入队成功则正常等待。

## 4. 用量统计口径

### 4.1 明细（`usage_logs`，每请求一行）

关键字段语义：

| 字段 | 口径 |
| --- | --- |
| `request_id` | 网关唯一请求 ID，即响应头 `X-Request-Id` |
| `user_id` / `api_key_id` | 下游调用主体（按网关 Key 解析） |
| `channel_id` / `model` / `upstream_model` | 实际命中的渠道、对外模型名、上游真实模型名 |
| token 三字段 | 上游 `usage` 实际值（`input/cached/output`） |
| `total_cost` | §1.2 计算的实际费用（美元） |
| `duration_ms` / `ttft_ms` | 总耗时 / 首 token 时间（流式） |
| `status` / `error_code` | `success / error / ...`；失败原因见 [附录](../03-附录.md) |

### 4.2 日汇总（`user_daily_stats`，按用户×日聚合）

```
按 (user_id, stat_date=created_at 所在自然日 UTC/本地时区) 聚合：
  total_input_tokens / total_output_tokens / total_cached_input_tokens / total_tokens
  total_cost                    ← 该用户当日全部请求费用和
  request_count / success_count / error_count
```

- 聚合以**结算完成**为准（含成功与部分成功计费的请求；网关侧未入账的拒绝不计数）。
- `last_processed_id` 记录聚合进度（`usage_logs.id` 游标），便于重跑对账。
- 报表只读 `user_daily_stats`，需要精确明细再查 `usage_logs`。

### 4.2.1 增量聚合与刷新（Redis → 每日表）

- 每次请求结算写 `usage_logs` 后，**同步**把增量写入 Redis Hash `stats:delta:{YYYY-MM-DD}`（按 `stats.timezone` 归日；费用以 ×1e8 整数存 `cost_micro` 避免浮点漂移；`_max_id` 记录当日 `usage_logs` 最大 id）。
- 短定时任务（`stats.flush_interval_seconds`，默认 5s）对每个日期键执行 **RENAME** 到 `stats:delta:flushing:{date}:{ts}` 取得一致性快照（此时并发新增会自动写入被重建的 live 键，互不冲突），再按用户 UPSERT 增量到 `user_daily_stats`；成功后删除快照键。
- 失败（如 DB 异常）时把快照键**合并回 live 键**并告警，下轮重试，保证不丢数据。
- Redis 不可用时降级为直接对 `user_daily_stats` 做增量 UPSERT。

### 4.3 费用归属

- **费用归属主体 = 用户（user_id）**，由网关 Key 解析确定；日汇总天然按用户聚合，满足"以下游（用户）为聚合单位统计 token / 次数 / 费用"。
- 渠道维度消耗（`channel_id` 花了多少钱）由 `usage_logs` 索引直接查询，供成本分析。

## 5. 路由 · 负载均衡 · 熔断（概要）

本文件为接口契约文档，此处仅给下游可观察语义，完整算法见实现文档：

| 能力 | 行为 |
| --- | --- |
| 模型匹配 | 请求 `model` ↔ `channel_models.model_name`（对外名），`enabled=true` 且渠道 `status=1` 的渠道为候选 |
| 负载均衡 | 候选按 `priority`（大者优先）分组，组内按 `weight` 加权**无放回**依次尝试；整组失败才降级到下一优先级（`routing.try_next_priority`，可用 `max_attempts_per_priority`/`max_total_attempts` 限制） |
| 粘性路由 | 默认开启：按 **会话** 维度用 Redis 亲和，键为 `affinity:{user_id}:{session}:{model}`；会话标识优先取请求头 `X-Session-Id`，其次请求体 OpenAI `user` 字段，均无则回退到用户维度（`_user`）。粘性渠道只要可用（active、未熔断、有该模型映射）就**优先于优先级**；不可用则重选并刷新亲和（TTL `routing.sticky_ttl_seconds`，默认 1800s） |
| 健康/熔断 | 上游连续失败/超时达到阈值 → 熔断（gobreaker），熔断期内不路由该渠道；健康渠道不足时错误码见 [chat-completions §4](chat-completions.md) |
| 失败切换 | 发送首字节前失败可在候选渠道重试；发送后不切换；切换时先解冻再对新渠道重新冻结 |
| 同渠道重试 | 每个渠道先重试 `routing.max_retries_per_channel` 次（默认 2），仍失败才按优先级换下一渠道；非流式与流式统一 |
| 流式重试 | **仅"尚未向下游写出任何字节"时**同渠道重试；一旦写出内容后失败即终止（补发 SSE `error` 事件 + `[DONE]`，不重试以免重复内容） |
| 空闲超时 | 流式读取超过 `upstream.stream_idle_timeout_seconds`（默认 60s）无数据 → 判定上游卡死并中断；SSE 内嵌 `error` 事件同样视为失败 |
| 下游中断 | 客户端断开即取消上游请求并关闭连接（看门狗），按**已收完整块**分词估算结算，及时止损 |
| 渠道余额 | 每渠道可维护本地估算余额（`channels.balance`，`null`=不限）；候选剔除 `balance <= routing.low_balance_threshold` 的渠道；每笔结算按网关费用扣减渠道余额（含场景2/3），管理员可经 `PUT /admin/channels/{id}/balance` 核对调整 |
| 余额 | 请求前按所选渠道单价预冻结（余额不足 → `429 insufficient_quota`），请求结束按实际 usage 结算多退少补（见 §2） |

## 6. 时区约定

`user_daily_stats.stat_date`、限流的 `rpd/tpd` 窗口按**网关配置的统计时区**（默认 UTC）划分自然日；管理端查询可指定 `timezone` 参数做换算。见 [附录](../03-附录.md)。
